Flagship case · In development

Learning from Historical Fraud Events

Exploring whether confirmed historical fraud events can reveal behavioral patterns useful for future risk prioritization.

PythonSQLFeature EngineeringMachine Learning

The question

Could historical inspection outcomes become a structured analytical learning problem rather than remain only retrospective records?

The difficult part

Repeated events, incomplete time series, unequal measurement density and event timing affected what could safely be learned.

Analytical design

I structured the work around fraud events, built pre-event / event / post-event windows, engineered behavioral features and segmented chronology quality before model experiments.

Historical events→Time windows→Behavioral features→Quality segmentation→Model validation
Engineering decision. Modeling did not start with an algorithm. I first separated observations with usable chronology from those whose history was too incomplete to support the same analytical claims.
Scope discipline. The current prototype is historical behavioral classification, not a production fraud detector. Deployable scoring requires a separate reference-date pipeline that cannot use future information.

Process automation

From Manual Reporting to an Automated Data Pipeline

Automating repetitive report retrieval and turning it into a recoverable workflow for operational analysis.

PythonSeleniumValidationScheduling

Pain point

Analysis depended on repeatedly navigating an internal reporting interface, configuring date windows, waiting for exports and preparing downloaded files.

How it evolved

The first goal was fixed-window report retrieval. It grew into dynamic date handling, download checks, validation, structured storage, duplicate protection, logging and catch-up logic for missing periods.

Why Selenium?

The required workflow was exposed through a user interface rather than an accessible integration endpoint, making browser automation a pragmatic integration layer.

Schedule→Missing-period check→Browser automation→Validation→Processing→Log
Team workflow improvement

Standardizing Repetitive Data Preparation

A small VBA utility that captures the working philosophy behind many of my projects.

OBIEEExcelVBA

What I noticed

A detailed operational export used in field analysis contained dozens of columns, and analysts repeatedly removed the same unnecessary fields by hand.

Before coding

I asked the engineers using the report which fields were actually required and converted the shared requirement into a reusable checklist.

Build

The macro evaluates report headers against the agreed keep-list and removes fields outside the analysis scope automatically.

Export→Header check→Approved fields→Analysis-ready dataset
The value was not technical complexity. It was eliminating a repetitive preparation step and standardizing how the team started the analysis.
